# Operaciones y Verificación de Cron en Hermes

Habilidad canónica para gestionar, depurar y auditar todas las tareas programadas (cron jobs) de la flota de agentes Hermes, garantizando entregas fiables a Discord y consistencia en los entornos de ejecución.

---

## Cuándo usar esta Skill (Triggers y Síntomas)

Usa esta skill inmediatamente cuando se presente cualquiera de estas situaciones:
- Peticiones del usuario: *"por qué falló la tarea de la noche"*, *"el cron no mandó el reporte a Discord"*, *"crea un cron para vigía"*, o *"audita las tareas programadas"*.
- Diagnóstico de jobs que aparecen como activos pero no producen salida o fallan con errores de permisos (`Errno 13`) o archivos no encontrados (`ENOENT`).
- Configuración de alertas automáticas, watchdogs y entrega de reportes recurrentes.

---

## Arquitectura de Ejecución: La Trampa de los Dos Tickers

Un job en Hermes puede ser reclamado por uno de dos planificadores con vistas de sistema de archivos completamente distintas:

| Ticker / Planificador | Usuario | Resolución de `/opt/data` |
|---|---|---|
| **Gateway (`gateway-default`, s6)** | `uid 10000` (namespace contenedor) | El árbol compartido real del contenedor (`/opt/data`). |
| **Root ticker (Hermes Desktop / Host)** | `root` (namespace del host) | Directorio del host; el árbol real vive en `/root/hermes-agent-legacy-docker/data` o montaje persistente. |

**Consecuencia**: Un script que hardcodea `/opt/data/...` funciona si lo reclama el gateway, pero muere con `FileNotFoundError` si lo reclama el host.

### Regla para Wrappers de Cron
Todo script wrapper de cron debe auto-detectar su entorno antes de ejecutar:

```bash
IN_CONTAINER=0
[ -f /.dockerenv ] && IN_CONTAINER=1

run_cmd() {
  if [ "$IN_CONTAINER" = "1" ]; then
    bash -c "$1"
  else
    docker exec -u 10000 hermes-agent bash -c "$1"
  fi
}
```

## Verificación en Vivo bajo Namespaces (`nsenter`)

Para diagnosticar exactamente lo que ve el contenedor del gateway sin suposiciones:

```bash
# 1. Obtener el PID del proceso gateway
G_PID=$(pgrep -f "hermes.*gateway" | head -1)

# 2. Entrar al namespace de montaje y usuario (uid 10000)
nsenter -t $G_PID -m -S 10000 -u -- python3 -c "import os; print(os.listdir('/opt/data'))"

# 3. Comprobar permisos de escritura reales
nsenter -t $G_PID -m -S 10000 -u -- touch /opt/data/cron/output/test_write.tmp && rm -f /opt/data/cron/output/test_write.tmp
```

Si el comando falla con permisos, reparar desde el host:
```bash
chown -R 10000:10000 /opt/data/cron/output/
```

## Gotchas y Errores Críticos Detectados en Producción

1. **Archivos creados por root**: Si ejecutas pruebas manuales como `root` que escriben en `/opt/data`, dejas trampas de sólo lectura para `uid 10000`. Siempre haz `chown -R 10000:10000` en los archivos creados.
2. **Serialización de terminal background**: Al lanzar procesos en segundo plano con `terminal(background=True, notify=True)`, el valor `notify` debe ser booleano estricto. Si se serializa como cadena `"True"`, el runtime arroja error.
3. **Salida limpia para eventos accionables**: Los cron jobs no deben imprimir basura en stdout si no hay error; solo emitir salida cuando requieran acción para no saturar los canales de alerta.
4. **El `python3` del PATH del cron es el intérprete bundled de Hermes (sin módulos de terceros)**: los scripts de cron resuelven `python3` al intérprete empotrado (ej. 3.14) que NO incluye PyYAML ni otras dependencias externas. Un script que lee secretos con `python3 -c "import yaml"` termina con KEY vacía → `EXTRACT_ERROR` nocturno recurrente y difícil de ver porque el error es silencioso. Regla: en scripts de cron, invocar SIEMPRE `/usr/bin/python3` por ruta absoluta (el sistema tiene PyYAML y el stack completo); verificar antes con `/usr/bin/python3 -c "import <mod>"` cada módulo no-stdlib que el script use.
5. **El ledger no se autolimpia: `failure_streak`/`last_status` persisten tras la recuperación** — un job que falló una vez y hoy entrega bien sigue apareciendo como `error` en `jobs.json`, y los informes matutinos lo reportan como caído (falsa alerta). Protocolo de auditoría antes de creer un "fallo": cruzar `jobs.json` contra las entregas reales en `logs/gateway.log` / `logs/errors.log` del día del fallo. Firma de despacho falsa-negativa conocida: `cron external worker exited before ownership acknowledgement (exit -15)` = worker systemd scope terminado por SIGTERM a los ~8 s; si gateway.log muestra la entrega del mensaje ese día, el job funcionó y solo el ledger quedó sucio. Limpiar el streak manualmente tras confirmar la entrega. Causa raíz confirmada y con pruebas en el repo (ver #6): no es el worker el que falla, es el dispatch que muere y el ticker que re-dispara.
6. **Firma `exit -15` antes del ack = doble disparo del mismo instante**: si el systemd scope del worker muere por SIGTERM antes de publicar el ack, el scheduler registra `dispatch failed` (`mark_job_run(False)` + aviso de crash), pero el job sigue vencido → el ticker lo re-dispara en proceso (`source=builtin`) segundos después y ESE intento es el que corre y entrega. Resultado: una entrega correcta + un aviso de falso fallo + `failure_streak` sucio, y el mismo instante ejecutado DOS veces (riesgo de efectos duplicados si el primer worker alcanzó a actuar). Contratos verificados con pruebas (tests/cron/test_dispatch_failure_terminal.py, verdes): (a) un fallo pre-ack deja el intento TERMINAL — `recover_interrupted_executions()` devuelve 0, la recuperación de dead-owner NUNCA re-ejecuta ese intento; (b) un ack publicado gana sobre el exit code (el bucle revisa `ack_path.exists()` antes de `process.poll()`), así que ack + muerte -15 es handoff válido, no fallo. El arreglo pendiente (rama fix/cron-dispatch-ack-ledger, spec en spec-F7.md) es consumir el instante programado al fallar el dispatch pre-ack; NO introducir reintentos automáticos sin causa raíz.
7. **Forense de dispatch fallido: dónde están las pruebas y cómo leerlas**: (a) cada perfil tiene su propio ledger — default en `/opt/hermes-agent-data/cron/executions.db`, los demás en `/opt/data/profiles/<perfil>/cron/executions.db`; cruzar el job_id del error contra TODOS los ledgers antes de concluir que "no corrió"; (b) `scheduled_instant` se guarda en UTC y `started_at` en hora local: un disparo de 06:00 (-05) aparece como instante `T11:00` — correlacionar sumando 5 h, no comparando a ojo; (c) para desmentir o confirmar hipótesis sobre el handoff, escribir pruebas sonda modeladas en `tests/cron/test_restart_safe_worker_death_evidence.py`: worker falso que adopta/escribe ack/muere con SIGTERM + monkeypatch de `tools.process_registry.restart_safe_gateway_child_argv` devolviendo `GatewayChildDispatch("degraded", [sys.executable, str(worker), *flags])`; correr con `scripts/run_tests.sh tests/cron/<archivo>.py`; (d) en la rama de fallo el scheduler borra el stderr del worker (`stderr_path.unlink`): si necesitas la causa del TERM, capturarla ANTES de que el incidente se cierre o instrumentar la conservación del tail en el incidente.
9. **Store muerto: un job creado sin contexto de perfil puede quedar en un store que ningún ticker reclama y nunca correr** (verificado en vivo, incidente informe de pagos 20:00): `hermes cron create` ejecutado desde la sesión default registró el job en el store central (`/opt/data/cron/jobs.json`), pero los jobs que sí tickean viven en `profiles/<perfil>/cron/jobs.json`; `hermes cron tick` NO ejecuta el job del store muerto (confirma el diagnóstico, no lo repara). Síntoma: job activo en el store, sin línea de ejecución ni en logs ni en ledger, indefinidamente. Protocolo: (a) localizar en cuál jobs.json vive el job antes de culpar al script; (b) recrear el job con el perfil dueño en el entorno del comando (`HERMES_PROFILE=<perfil> hermes cron create ...`), manteniendo la entrega al hilo destino en la config del job; (c) borrar el duplicado del store muerto; (d) verificación final = esperar el primer slot real y confirmar la entrega en el chat (un job puede estar 'correcto' y no haber corrido nunca: su primer vencimiento puede ser futuro). Variante verificada post-fix: un job creado con `HERMES_PROFILE=helmer` puede terminar en el store central Y tickear — lo determinante es la env del comando creador, no solo la ruta del archivo; ante la duda, la prueba de verdad es el primer disparo real, no la ubicación del JSON.
8. **Variante `exit -15` POST-ack ("after adopting this execution… whether side effects ran is unknown") = worker muerto a mitad de corrida, no arranque en frío**: el worker SÍ adoptó y publicó ack y luego recibió SIGTERM externo. Protocolo de triaje verificado en vivo (incidente sync-connections-map 15:00): (a) descartar doble despacho contando los scopes `hermes-worker-cron-<job>-exec-*` arrancados en ese segundo con `journalctl --user -S <t1> -U <t2>` SIN filtro de grep (el ERROR del gateway aparece ~11 s después del "Started" del scope y el scope sigue consumiendo CPU ~10 s más: el wrapper muere antes que el cgroup); (b) descartar reinicio del gateway: `systemctl show hermes-agent -p NRestarts -p MainPID` — 0 reinicios + PID estable = el killer es EXTERNO a Hermes (ni `cron/` ni `gateway/` envían TERM a estos workers, confirmado por grep exhaustivo); (c) descartar OOM: systemd-oomd inactivo + RAM libre; (d) efectos: revisar `cron/output/<job_id>/` (status "silent (empty output)" = sin cambios) y los mtimes de los archivos que el script escribe; si el script es idempotente, el siguiente tick se auto-repara y NO re-ejecutar a mano. Variante sin rastro (verificado en PROD, 4 jobs muertos a la vez y aparte): muerte en <1 s tras el arranque (duración `started_at→finished_at` en executions.db) + `grep killguard /opt/data/logs/*.log` SIN entradas a esa hora + sin línea `Received SIGTERM`/`Shutdown context` en gateway.log = el TERM NO salió por las rutas instrumentadas: el runner solo loguea killpg si `agent.killguard` importa; si falla el import, hace `killpg` crudo sin dejar rastro. Regla: con ese triage vacío, reportar "origen externo no identificado" y pedir evidencia de kernel — NO atribuir timeout/OOM/restart sin una de esas tres evidencias (cada una descarta una clase de causa distinta: duración larga descarta timeout, log de killguard descarta el propio runner, gateway.log descarta reinicio).
Límite duro: identificar QUIÉN envía la señal exige evidencia de kernel (regla auditd sobre la syscall `kill` o bpftrace) que requiere root — como uid 10000 no es posible sin sudo. El RuntimeWarning `<frozen runpy>:130 … 'cron.scheduler' found in sys.modules` en el stderr es cosmético, no la causa.
10. **Las variables gestionadas por Hermes ya NO están en `/opt/data/.env` (migración a la fuente de secretos del perfil, v0.22.x)**: los scripts de cron que parsean `.env` para obtener credenciales (p.ej. `DISCORD_BOT_TOKEN`) rompen con `FileNotFoundError` o valor vacío — el gateway las aplica al arrancar desde la fuente de secretos del perfil y el `.env` dejó de contenerlas. Patrón de resolución verificado en vivo para scripts standalone: (1) `os.environ.get(<VAR>)` directo; (2) si falta, `sys.path.insert(0, '/opt/hermes-agent')` + `from hermes_cli.env_loader import hydrate_profile_secret_sources` → `hydrate_profile_secret_sources('/opt/hermes-agent-data').get(<VAR>)`; (3) fallback legado `.env`; (4) si todo falla, `raise SystemExit(...)` — NUNCA `print("ERROR")` + `return`: el job queda `ok` en el ledger (falso verde, incidente higiene-tags 26-oct). Verificación sin efectos secundarios: `python3 -c "import sys; sys.path.insert(0,'/opt/hermes-agent'); from hermes_cli.env_loader import hydrate_profile_secret_sources; print(bool(hydrate_profile_secret_sources('/opt/hermes-agent-data').get('DISCORD_BOT_TOKEN')))"`. Scripts heredados aún con el patrón viejo sin migrar: `dashboard_stale_guard.py`, `discord_*.py`, `ncl_discord_mcp.py` (no cronean hoy; migrar al tocarlos).
11. **Remedio persistente ante despacho de worker crónicamente inestable: backstop a cron de sistema (validado 27-oct, publicador del calendario y sync-connections-map):** cuando un job crítico acumula fallos reales `exit -15` pre-ack (la ventana de publicación SÍ se pierde, no es falso verde), no esperar al fix del dispatch: migrar el disparo al cron del sistema, donde el despacho no falla. Receta: (a) probar el script como `hermes` antes de instalar (`sudo -u hermes /usr/bin/python3 <script>`); (b) crear `/etc/cron.d/<nombre>` con `sudo -u hermes /usr/bin/python3 <script> >> <log> 2>&1` a la misma frecuencia del job Hermes, respetando la ventana de publicación; (c) proteger el script con el canary watchdog; (d) PAUSAR el job de Hermes (`hermes cron pause <id>`) para cortar el spam de alertas fallidas al WhatsApp del Admin; (e) verificación = primera corrida real entregando al canal destino. El backstop del publicador tomó el tick de 12:00 el mismo día y publicó las 10 piezas aprobadas.
12. 27. **Inventario masivo de jobs cross-host (DEV 104/PROD 67+ = >170 jobs): `hermes cron list` NO tiene `--json`** — parsear los stores `jobs.json` directamente en Python: `/opt/data/cron/jobs.json` (central) + `/opt/data/profiles/*/cron/jobs.json` + `/opt/hermes-agent-data/profiles/*/cron/jobs.json`; en PROD todo vive bajo el `jobs.json` del contenedor. Reglas de la receta: (a) editar SIEMPRE vía CLI (`hermes cron edit`), nunca escribiendo el JSON (el gateway no se entera); (b) cada job de store de perfil exige `HERMES_PROFILE=<perfil>` en el entorno del comando de edición; (c) heredocs de terminal que contienen palabras como stop/restart/uninstall disparan el kill-guard del gateway — escribir el script a un archivo con write_file y correrlo por ruta; (d) verificar el edit releyendo el campo en jobs.json, no confiando en el eco del CLI.

28. **Gate barato con `--monitor-script` (flags verificados en build v0.22.6: `--monitor-script`, `--catch-up {on,off}`, `--grace-minutes`, `hermes cron cancel/incidents/notepad`):** un job que pregunta o reporta NO debe despertar al LLM si no hay nada nuevo — un script monitor decide: si su condición devuelve 'sin cambios', el job no corre ni gasta ni manda mensaje vacío. Aplicarlo a todo job de pregunta diaria y a vigías que hoy corren sí o sí. Y `catch_up` es un flag POR JOB, no de config global: `hermes cron edit <id> --catch-up off` (en store de perfil: `hermes -p <perfil> cron edit <id> --catch-up off`). NO afirmar que solo existe el flag global `cron.catch_up_missed` sin haber verificado `hermes cron edit --help`. Ámbito recomendado: apagarlo en jobs con cadencia ≤60 min (un disparo atrasado sub-horario no justifica la ráfaga tras un reinicio) y mantenerlo en informes diarios/críticos que sí deben recuperarse si el host estuvo caído. Aplicación en lote: escribir el lote a un script con write_file y correrlo por ruta (evita el kill-guard de heredocs), luego verificar releyendo `catch_up is False` en TODOS los stores, no confiando en el eco del CLI. Nota: el hook `pre_llm_call` con acción `block` (veto antes de inferencia, verificado en `agent/turn_context.py`) es un hook de PLUGIN (`ctx.register_hook()`), no una línea de config — usarlo exige escribir un plugin por perfil.

**Recordatorio one-shot al DM de una persona específica (validado 28-oct):** `deliver: discord:<chat_id>` NO acepta el user_id de Discord — hay que resolver primero el ID del canal DM. NO intentar obtenerlo vía REST del bot: `GET/POST /users/@me/channels` responde `401: Unauthorized` aunque el token funcione en endpoints de guild. Fuente fiable en vivo: `sqlite3 /opt/hermes-agent-data/state.db` → tabla `sessions`, buscar `origin_json LIKE '%<user_id>%'`; la fila DM se distingue por `guild: None` y `chat_name` = username del destinatario; el canal es `origin_json.chat_id`. Receta de creación (cronjob_manage action=create): `schedule` con ISO absoluto local (ej. `2026-10-28T08:00:00`, se interpreta en TZ Bogotá), `repeat` default una vez, `deliver: "discord:<dm_channel_id>"`, y prompt AUTOCONTENIDO que ordene responder con EXACTAMENTE el mensaje aprobado (la respuesta final del job es lo que se entrega, sin contexto del chat de origen). Verificación inmediata: campos `next_run_at` y `deliver` de la respuesta de creación (estado `scheduled`).

13. **Firma `cannot read dependency environment: <HERMES_HOME>/installs/<id>/facts.json` = VENTANA DE AUTO-ACTUALIZACIÓN del gateway, no corrupción ni disco (2ª ocurrencia confirmada, 03-nov-2026; la 1ª el 17-oct se diagnosticó mal y se perdió ~4 h):** durante un self-update el bootstrap regenera el árbol `installs/<id>/` y mientras dura (~8 min) los hooks de entorno fallan **fail-closed**: primero caen navegador/terminal/execute_code y acto seguido TODOS los crons disparan el mismo error. Protocolo: (a) NO perseguir corrupción de archivos ni reparar a mano — se arregla solo al terminar el bootstrap; (b) confirmar la causa con `grep -i boot_bootstrap <gateway.log> | tail` → línea `code changed to <hash>, running steps` minutos antes del primer fallo, y `ls -la installs/<id>/` con mtime = esa ventana; (c) medir el impacto REAL en el ledger/entregas antes de alarmar (los backstops a nivel de sistema operativo de #11 publican igual aunque el cron de Hermes esté caído); (d) re-verificar al cerrar la ventana: `facts.json` legible + `hermes cron run <id>` → `succeeded` + herramientas de ejecución respondiendo; (e) si coincide con horas de publicación, la mitigación es estructural (hook fail-open durante regeneración / ventana de update controlada), no parche local. Detalle diagnóstico: el primer síntoma suele ser 'el navegador no responde' unos minutos ANTES de que el error aparezca en los crons — ahí ya empezó la ventana.

14. **Job de informe recurrente en un foro: el post se crea con su mensaje y sus tags en UNA sola llamada, y el cron entrega a `discord:<thread_id>` (validado 03-nov-2026, estudio semanal de upstream):** crear el hilo con `POST /channels/{forum_id}/threads` enviando `{name, auto_archive_duration: 10080, applied_tags: [<tag_id>...], message: {content: <informe inicial>}}` — el informe de la primera corrida entra como mensaje raíz, sin POST extra. Después: `hermes cron create "30 6 * * 1" --script <script>.py --no-agent --deliver "discord:<thread_id>"`. En modo `--no-agent` **stdout ES el mensaje**: mantenerlo ≤1900 chars (se parte o se rechaza por encima de 2000) y hacer que el script imprima SIEMPRE algo, incluso en su `except` final — un script que muere en silencio produce un job en verde sin contenido. Receta completa y verificación en `references/entrega-foro-discord.md`.
15. **Higiene inversa: un job que hace curl al webhook de Discord SIN `?thread_id=` fijo crea un hilo NUEVO por corrida (nombre dinámico tipo `vigia-report-2026-11-03`), y cualquier limpieza masiva de hilos los borra → el job los recrea → bucle de deshacer (lección de Fase 0 con Bob, 03-nov-2026):** (a) FIX DE RAÍZ primero: fijar `?thread_id=<id>` en la URL del webhook del job (hasta entonces NO borrar los hilos dinámicos existentes); (b) la guarda de borrado masivo debe tener lista de patrones de hilo dinámico (`vigia-report`, `latido-flota`, `informe-vigia`, ...) aplicada ANTES del chequeo de webhooks y del `BORRARIA` — si un hilo es a la vez dinámico y alimentado por webhook, gana el SKIP; (c) pitfall de normalización (probado importando el módulo real): normalizar solo acentos+minúsculas NO basta — colapsar separadores a espacio en AMBOS lados (`re.sub(r"[\s_.\-]+", " ", n).strip()`), porque `Latido flota Hermes`, `Vigia informe 0800`, `vigia-auditoria-2100` y `Digest de Competidores IA` NO matchean patrones escritos con guion y se cuelan como borrables; (d) trazabilidad del dry-run: el manifiesto debe dejar acta de lo que SE BORRARÍA (`man["threads"].append({"id": tid, "name": name, "accion": "borraria"})` en la rama sin `--apply`), no solo de los SKIPs — stdout es efímero y sin acta la fase de apply no tiene contra qué compararse. Regla general: toda guarda de borrado masivo debe normalizar identificadores de forma canónica y dejar acta de lo que HARÍA, no solo de lo que omite.

16. **Receta de purga de jobs muertos (validada 03-nov-2026, Fase 0, 31→28 jobs):** (a) SIEMPRE backup previo `cp <ruta>/jobs.json jobs.json.bak-fase0-$(date +%Y%m%d-%H%M%S)`; (b) borrar SOLO tres clases verificadas: deshabilitados desde semanas ya reemplazados (cruzar contra el reemplazo real — p.ej. job deshabilitado cuyo trabajo lo hace una línea de `/etc/cron.d`), `once` vencidos hace días, y guardas de infraestructura ya retirada (dashboard muerto); (c) NO borrar jobs habilitados aunque parezcan redundantes — un job que verifica el éxito de otro (confirmar) se consolida en su fase propia, no en la limpieza; (d) verificación: `cronjob_manage action=list` y confirmar el conteo exacto antes/después (31→28), no fiarse del eco del delete; (e) dejar bitácora en el acta de auditoría con job_id, estado previo y motivo de cada borrado. 17. **Fallo de DNS en un contrato cross-host ≠ ausencia de ruta (corrección factual verificada 03-nov-2026, aplica a contratos de entrega de informes entre DEV y PROD):** al validar la dirección de un canal de entrega, `ssh -o BatchMode=yes dev hostname` desde PROD falla con `Could not resolve hostname dev` y `getent hosts dev` devuelve rc=2 — eso solo prueba que falta el alias DNS. La ruta REAL existe: como root en el host PROD, `ssh root@100.86.8.81` (Tailscale de DEV) conecta rc=0 → `vmi3151337`, con la `id_ed25519` de PROD autorizada en DEV desde el 05-oct.
