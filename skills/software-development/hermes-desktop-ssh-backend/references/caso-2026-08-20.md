# Caso real 20/08/2026 — Desktop SSH a VPS: de "no me deja" a todo funcionando

Ambiente: Hermes Desktop en Windows (usuario `wwwko`) → VPS Contabo
`147.93.3.250` (hostname `vmi3151337`), usuario `root`, clave SSH
`~/.ssh/id_ed25519` (definida en `C:\Users\wwwko\.ssh\config`).

## Fase 1 — "Update remoto de hermes pero no me deja"

Síntoma en `C:\Users\wwwko\AppData\Local\hermes\logs\desktop.log`:

```
[ssh-lifecycle] located hermes at /root/hermes-agent-legacy-docker
Desktop boot failed: The remote Hermes install does not support
--ssh-session-token-file and --ssh-owner-nonce. Update Hermes on the remote host
to continue using Desktop SSH mode.
```

### Diagnóstico

1. `remoteSupportsSshOwnership` corre `hermes serve --help | grep` en remoto.
2. El binario real `/usr/local/bin/hermes` SÍ tiene los flags:
   ```
   [--ssh-session-token-file PATH] [--ssh-owner-nonce NONCE]
   ```
   → probado: `hermes serve --help 2>&1 | grep -cE "ssh-session-token-file|ssh-owner-nonce"` = 2.
3. Pero Desktop resuelve `hermesPath` desde `connection.json`
   (`C:\Users\wwwko\AppData\Roaming\Hermes\connection.json`):
   ```json
   "remoteHermesPath": "/root/hermes-agent-legacy-docker"   // ← un DIRECTORIO
   ```
   Ejecutaba `/root/hermes-agent-legacy-docker serve --help` → `Is a directory` → NO.

### Fix aplicado

```json
"remoteHermesPath": "/usr/local/bin/hermes"
```
(Con la app cerrada; luego se reabrió.) Log tras el fix:

```
located hermes at /usr/local/bin/hermes
remote hermes version: Hermes Agent v0.20.4 (2026.8.18)
spawned remote dashboard pid=2730310
Remote Hermes backend is ready
```

## Fase 2 — "Ya conecta pero no veo mis sesiones/bots/Ragnar"

El backend SSH usa `HERMES_HOME=${HERMES_HOME:-$HOME/.hermes}` = `/root/.hermes`:

```
/root/.hermes/state.db            = 229 KB   (vacío)
/root/.hermes/profiles/           = no existe
/root/hermes-agent-legacy-docker/data/state.db  = 164 MB   (los datos reales)
/root/hermes-agent-legacy-docker/data/profiles/ = ragnarcho, shared
```

### Fix aplicado (bindear HERMES_HOME en sesiones SSH)

```bash
printf 'PermitUserEnvironment yes\n' > /etc/ssh/sshd_config.d/99-hermes-env.conf
umask 077
printf 'HERMES_HOME=/root/hermes-agent-legacy-docker/data\n' > /root/.ssh/environment
chmod 600 /root/.ssh/environment
sshd -t && systemctl reload ssh
```

Verificación:
```
ssh root@147.93.3.250 'echo $HERMES_HOME'   → /root/hermes-agent-legacy-docker/data
hermes profile list                         → default, ragnarcho, shared
```

## Fase 3 — "le falta inferencia"

`/root/.hermes/config.yaml` apuntaba a OpenRouter (`claude-opus-4.6`) **sin key**.
El config funcional estaba en `/root/hermes-agent-legacy-docker/data/config.yaml`:

```yaml
model:
  api_key: <key>
  base_url: https://api.nan.builders/v1
  default: deepseek-v4-flash
  provider: NaN-Builders
```

Fix: alinear `/root/.hermes/config.yaml` con ese bloque (backup en
`config.yaml.bak.desktop`). Key verificada: `curl -o /dev/null -w "%{http_code}"
https://api.nan.builders/v1/models -H "Authorization: Bearer $KEY"` → **200**,
y `/v1/chat/completions` con `deepseek-v4-flash` → **200**.

## Fase 4 — proceso stale

El dashboard remoto lanzado antes de los fixes (pid 2730310) seguía vivo y Desktop
lo reutilizaba con la config vieja. Fix:

```bash
kill 2730310
rm -rf /root/.hermes/desktop-ssh/*
```
+ re-login en Desktop → todo visible (Ragnar, bots, sesiones).

## Lecciones

- El mensaje "Update Hermes on the remote host" puede ser engañoso: a veces es la
  **ruta** del binario, no la versión.
- Desktop SSH **nunca** reutiliza el `serve` 9112; lanza su propio backend aislado.
- El home de datos lo decide el entorno SSH (`HERMES_HOME`); sin él cae a `~/.hermes`.
- El diálogo "instalar subsistema Linux / WSL" es falso aviso: el modo SSH usa
  ssh.exe / Git Bash, no WSL.
